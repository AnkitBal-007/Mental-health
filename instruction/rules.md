# Project rules

These apply to every teammate and every AI agent (Antigravity or otherwise) working on this repo.

## Scope discipline

- Each agent/workspace only edits files inside its assigned folder (`/backend`, `/frontend`, `/chatbot`, `/ml-pipeline`, `/simulation`). Cross-folder changes go through a human-reviewed integration pass, not an agent working unsupervised across boundaries.
- Don't restructure the top-level folder layout without team agreement — other agents/workspaces depend on the paths staying stable.

## Data & privacy rules

- Never use real victim data, even for testing. Synthetic data only, generated by `/simulation`.
- Every victim record must use an anonymized/pseudonymized ID — never store or display real names in any UI, log, or seed script.
- Any new field added to the victim/check-in schema must be justified against "does the dashboard or scoring engine actually need this" — don't collect data for its own sake.
- No feature may auto-execute an intervention (contacting a victim, notifying police, closing a case). The system recommends; a human decides and confirms.

## AI/model rules

- Every distress score or alert shown in the UI must ship with an explanation. A bare number with no factor breakdown is not acceptable output from any module.
- Document which parts of the pipeline are rule-based vs. model-based in each module's README — this matters for explaining the system to non-technical reviewers.
- If a model is trained on synthetic data, say so explicitly in code comments and in the README — never let synthetic-data provenance get lost or implied to be real.
- Keep the escalation-prediction model simple enough that a human on the team can explain, feature by feature, why it flagged a given case. Avoid opaque deep models for this component.

## Code & review rules

- All risk-scoring and alert-threshold logic changes require review by a human teammate before merge — this is the part judges will question directly.
- Commit in small, working increments. Don't let an agent run unsupervised for hours before the first review checkpoint.
- Every new backend endpoint needs an example request/response in that module's README.
- No hardcoded secrets, API keys, or credentials in committed code — use environment variables and a `.env.example` file.

## Demo integrity

- Any screen or chart shown in the demo must be clearly labeled where the underlying data is synthetic.
- Don't claim real IVRS/SMS integration in the pitch — it's simulated in the prototype; say so plainly.

## Working with Antigravity agents

- Give each agent a scoped, specific prompt (see `phases.md`) — don't ask an agent to "build the whole system."
- Review agent output via screenshots/walkthroughs before accepting, especially UI and scoring logic.
- If an agent drifts off-spec or produces confused output, restart that workspace rather than patching a derailed session.
- Check Antigravity usage quota each morning of build week — don't assume today's limits hold for the whole hackathon.
